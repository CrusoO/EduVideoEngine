# ADR 0121: Opt-in render profiles and a page-ready timeout

Status: Proposed, 2026-11-27. The owner accepts the ADR. Builds on ADR 0093 (job guards), 0099 (the explainer pattern), 0103 (render speed: what was measured and which levers change bytes, which the owner decides), 0114, 0118 (strict gates), 0119 and 0120. Touches no frozen file and no item of section 15 of the architecture. `docs/ENGINE_INTERFACE.md` changes additively (section 10, contract 0.4): one optional request option; a request that does not use it is read, keyed and drawn as before.

**What this ADR does not do, stated first.** It does not change the default output. The standard render keeps its frame size, its encoder settings, its frame files and its concat list, and every existing build key, render key and request hash. It does not make the render faster by default: ADR 0103 records that the levers which change bytes are the owner's to decide, and this ADR only makes two of them available to a host that asks. The measurements below were taken on a machine short of memory the whole time and are single runs: they show a smaller file and an encode that overlaps the frames, not a proved speed-up.

## Context
- On the development machine (7.8 GB of memory, about 100 MB free most of the time) the render browser often cannot load the story page within 30 s, which is the fixed limit of Playwright's `goto` and `waitForFunction` (a previous agent saw "Chrome page-ready timeouts under memory starvation"). The failure was `page.waitForFunction: Timeout 30000ms exceeded` in the child's error output and `render_failed: the video export stopped (exit 1)` in the job: no word about memory, no way to ask for more time (workflow rule 13).
- ADR 0103 measured a 105 s video at 138.6 s of render on this machine: frames drawn 38%, encode (preset slow) 27%, the 5 s start of every ffmpeg call about 12% (voice finish), and recorded the levers that change bytes (a faster x264 preset, a smaller frame) as the owner's decision. Draft videos and low-end machines would trade size and finish for time.

## Decision
**1. The request option.** `options.render`, an optional strict object (`job/job.ts`):
- `profile`: `standard` (default) or `fast`. A closed enum; an unknown value, including `portrait`, is `invalid_request`.
- `pageReadyTimeoutMs`: a whole number from 30000 to 180000. Default 30000, the limit the render always had.
- Any other field is refused (the frame size and encoder settings are not the host's to set).

**2. Keys.** `storyOutputOptions` adds `render: "<profile>"` only when the profile is not `standard`, so a request with no `options.render`, with `render: {}`, with `profile: "standard"` or with only `pageReadyTimeoutMs` has exactly the build key it had (pinned in `tests/render-profiles.test.ts` from the unmodified code of wp-a at bc14ce8, for five fixtures: build key, sanitised story, placed story and page hash). The render key already contains the build key, so a non-standard profile changes both. `pageReadyTimeoutMs` is in no key: it changes no frame. The request hash (idempotency) does contain the whole request, as for `qa`.

**3. The `fast` profile** (`job/render-profile.ts`, `scripts/story-video.ts`):
- The page is laid out and drawn at 1920 by 1080 exactly as in every profile, and the encoder scales the picture to 1280 by 720 (`scale=1280:720:flags=lanczos`). So the placed story, the page bytes and the strict gates are the same as for `standard`: the text of a 720p video is the same share of the frame, and the 10 px minimum on a 390 px phone (ADR 0118) is a share of the width, so it holds for a 1280 px video too. What changes is the absolute size: the smallest text allowed by the gates is 2/3 as many pixels high in the file. A fractional device scale factor (draw at two thirds in the browser, so the browser does less work) was the first design; its screenshots stalled on the development machine at the time of testing, but screenshots of a plain page stalled too, so the cause was the browser and not the factor, and the factor was not proved either way. The encoder does the scaling, which is known to work. Drawing at the smaller size remains a possible later saving.
- x264 preset `veryfast`, `crf 23`, still `tune animation`; audio unchanged (the same `voice.wav`, aac 128k).
- Frames are not written as JPEG files with a concat list. They go to ffmpeg through a pipe, JPEG at quality 90, at a constant rate. The concat list gave each frame a duration (at least 30 ms) and the encoder's `fps` filter put the frame at the slot nearest its start time; `pipeRepeats` computes the same slot for each frame and writes the frame that many times, so a frame is on screen at the same time. Two frames that fall in one slot give the slot to the later (the earlier is not written). Frames are drawn by up to six pages out of order and written in order (at most one per page waits). The voice is mixed before the browser starts, because the encoder needs `voice.wav` when it starts; the mix does not depend on the frames. A failed frame or a failed browser stops the encoder.
- This changes bytes (smaller size, other encoder settings, JPEG quality, a pipe), so it is opt-in and in the key.
- Timing equality is argued from the arithmetic above and tested for the arithmetic only (`pipeRepeats`); the duration and output frame count of two jobs equal the standard render's, but it was not compared frame by frame.

**4. The page-ready timeout.** `pageReadyTimeoutMs(request, VIDEO_PAGE_READY_TIMEOUT_MS)`: the request's value, else the environment's, else 30 s; always 30 to 180 s. The environment value is read in `story-video.ts` through `readEnv()` (the engine's single reader; the test that greps for `process.env` still passes), must be a whole number of milliseconds inside the bounds, and is ignored otherwise (so a typo cannot make it one second or one hour). It is used for `page.goto` and for waiting for `window.__ready` of each of the pages. A timeout there throws `page-ready timeout: the render browser did not get the story page ready within N s, which usually means the machine is short of memory. Close other programs, or ask for more time with options.render.pageReadyTimeoutMs (30000 to 180000) or VIDEO_PAGE_READY_TIMEOUT_MS, and run the job again.` and the runner adds the same cause to the `render_failed` detail. The 30-minute render stage limit (ADR 0093) is unchanged.

**5. Not built: `portrait`.** A 1080 by 1920 phone video needs the scene composed on a tall canvas. The stage is a fixed 100 by 45 unit landscape box, the placement grid (ADR 0102), the layout, the templates (ADR 0119) and the strict gates are all defined on it, and a portrait stage would need its own coordinates for every one of them, not a different viewport. Putting the landscape stage in the top of a portrait frame would waste most of the frame and make text smaller, not more readable. It needs a portrait scene-layout design first; the enum is closed so that adding it later is an additive contract change.

## Measurements
Machine: Intel Core i5-1035G1, 7.8 GB RAM, Windows 11, ffmpeg 6.1.1 (ffmpeg-static), `LLM_MODE=replay`, `VIDEO_VOICE_WORKERS=1`, fps 12, render process pinned to 2 CPUs, 2026-11-27. Free memory was 13 to 290 MB for the whole session and the system was paging heavily (4 GB in the compressed-memory store; OneDrive and the search indexer held 3.2 GB and 2.4 GB of private memory; none of these is the engine). One heavy process at a time. **The timings are not a controlled comparison**: the voice-finish phase (several ffmpeg starts) varied from 4 s to 207 s between runs of the same code with the memory, so wall-clock totals say little; the per-phase numbers for frames and encode are more telling and are still single runs.

Browser. Playwright's default launch fell back to Microsoft Edge on this machine, and Edge's `page.screenshot` timed out for any page (even a one-line page) for most of the session, so a render through the unchanged runner hung and ended as a stage timeout (steps job: the 420 s limit was hit). All numbers below were taken with the render stage script run directly, in a scratch copy of `story-video.ts` that differs from the committed file only in launching Playwright's installed `chrome-headless-shell` (rev 1243) and using 3 pages (the committed code uses up to 6). Same browser and page count for every row.

In the fast rows the encoder runs while the frames are drawn, so the "frames drawn" and "encode" columns overlap and the total is what counts; the voice finish is done first. The much shorter voice finish in the fast rows is the memory situation of that moment and not an effect of the profile (it is the same mix code); do not read the wall-clock difference as a speed-up. What the profile does change, in these runs: the standard encode (50 s, 33 s, after the frames) is replaced by an encode that overlaps the frames; the file is 20 to 24% smaller.

**Default output unchanged: proved by bytes.** The lesson.mp4 of the pendulum job rendered by the unmodified code of wp-a (with only the two page-ready timeouts, the page count and the browser path changed in a scratch copy, as above) and by this branch's standard path have the same sha256, a0d70091bcbef6550961fe99536c524613616d68c2b3b0fcead716351793f256, 1,163,597 bytes. In addition the build keys, sanitised and placed stories and page hashes of five fixtures are pinned from the unmodified code in the tests. With Edge and the 30 s page-ready limit the unmodified code failed 4 of 4 times (`page.waitForFunction: Timeout 30000ms exceeded`) and the new code once, printing the new `page-ready timeout: ...` message; a render through Edge with the 180 s limit completed once (236 s, 1,208,922 bytes, a different file because the browser differs). One run of the new standard path failed with a missing frames folder at the encode step and could not be reproduced on three later runs; the cause is not known.

**Frames looked at.** Contact sheets (one frame every 4 s, 640 px wide tiles) of the steps template, standard and fast, were looked at side by side: the title, the four step boxes, the arrows and the caption are in the same places and appear at the same seconds in both, and the caption (the smallest text) is readable at 1280 by 720. The pendulum sheets show only the title and the captions: its drawn object does not appear in either profile on this machine (the same in the unmodified render), so that sheet says nothing about shapes. Duration (48.28 s and 17.25 s) and output frame count (579 for the pendulum) are equal in the two profiles. No frame-by-frame comparison of the profiles and no listening check of audio sync were done. The strict gates (ADR 0118) run on the placed story before the render, and the placed story is the same for every profile; a strict run of the fast profile through `pnpm video:job` was not done, so that it passes rests on this argument. The 720p file has 2/3 as many pixels in every text height; the smallest allowed text (10 px on a 390 px phone) is the same share of the width.

## Not decided here (the owner decides)
- Whether `fast` is good enough for drafts: the frames at 720p, the file size and the time have not been compared, by anyone.
- Whether the default of 30 s should rise (the safer default for starved machines) or stay (today's behaviour).
- Whether to build `portrait`, and the scene-layout design it needs.
- Whether the render should open its pages one after another on a starved machine (not done: it would change timing for everyone).

## Consequences
- Tests: `render-profiles.test.ts` (24 tests): the schema accepts the closed profiles and the bounds and rejects an unknown profile, `portrait`, a timeout of 0, 29999, 180001, a fraction, a string and NaN, unknown fields and `render` given as a word; the default and `standard` leave the keys (pinned) and `storyOutputOptions` unchanged; a non-standard profile changes the key and the timeout alone never does; five fixtures keep their key, sanitised story, placed story and page hash (pinned from unmodified code); `pipeRepeats` holds a frame for its duration and sums to the number of frames; the timeout resolver and the failure message.
- Mutation was not measured (Stryker cannot finish on the development machine).
- Risks: the `fast` profile was run through the render script on two jobs only and not through `pnpm video:job` (the runner's default browser could not take screenshots here); its frame timing equals the concat list's only up to the slot arithmetic; a pipe that is slower than the pages makes pages wait (bounded by memory of one frame per page); a screenshot that hangs still has no per-frame time limit (`page.evaluate` has none and `screenshot` has 60 s with 3 attempts, as before).
- Not built: `portrait`; per-frame timeouts around `page.evaluate`; a lower page count on a starved machine; a device scale factor below 1.
