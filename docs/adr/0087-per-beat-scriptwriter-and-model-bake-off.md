# ADR 0087: A scriptwriter that asks for one beat at a time, and a bake-off that picks the model by the engine's own rules

Status: proposed (agent, at the owner's request of 2026-10-23: build the model bake-off and the per-beat scriptwriter, tested with a fake client, and make no live call until the owner says the keys are in `.env`; the owner is asked to confirm this record). Supersedes nothing. Prompt `scriptwriter.v1` is untouched, so no recorded request changes key.

## Context
The model has two jobs in the engine: the planner chooses the arc and patterns from closed lists, and the scriptwriter writes the narration of claims the knowledge base already supports. Both answers are judged by code (the plan rules, `checkScript`, gates G1 to G7, SymPy). Which free model writes the best narration, and whether to ask for the whole script or a beat at a time, has never been measured: one model was tried, and it has since been retired by its provider (ADR 0060, 0075). The free tiers have small caps (Gemini 20 requests a day in our profile, OpenRouter free models 50, Groq 1,000 requests but 8,000 tokens a minute), so the choice also depends on requests and tokens.

## Decision
1. **`scriptwriter.v2` and `writeScriptPerBeat`** (`prompts/scriptwriter.v2.md`, `packages/pipeline/script/per-beat.ts`). One request holds one beat's claims, its position, the last two sentences the student heard (a formula placeholder is told as "the formula"), and optionally `feedback` (the messages of a rejected answer) and a `candidate` number. The rules of v1 stay; v2 adds style rules (speak to one student; the picture or example before the rule; no two sentences starting with the same word; no stock phrases; say an idea once, then why; continue from what was heard). Each answer is judged by `beatProblems`, the per-beat part of `checkScript` (extracted, behaviour unchanged), with the same single repair as before. The whole lesson is then judged by `checkScript` (assembly, gates, validators); a beat those messages name is asked for once more with them as `feedback`. A message that names no beat cannot be repaired by asking a beat again, so the script fails with it.
2. **Candidates.** `candidates: n` asks for n answers per beat (a different request each, so a different recorded key) and keeps the valid one with the best `narrationScore`. The score is the engine's own and judges only the manner of the telling: sentence length near what can be said in one breath, differing openings, no repeated sentence, no stock phrase. It is a heuristic, not checked against listeners.
3. **`buildLesson` takes `script: { mode: "whole" } | { mode: "per-beat", candidates? }`**; the default is unchanged.
4. **The bake-off** (`packages/pipeline/bakeoff`, `pnpm llm:bakeoff`). A run is one (model, lesson, strategy) build with a synthetic voice; the strategies are `whole`, `beat` and `beat3`. Rows record whether the plan and script passed, repairs, requests sent, tokens (from the ledger), seconds, gates, SymPy and the narration score; the ranking orders by builds passed, then passed without a repair, then narration, then requests, then tokens. Without `--go` it only prints what it would do (the models, keys present or not, requests against the daily caps) and sends nothing. With `--go` it records every answer under `dist/bakeoff/<run>/fixtures/<model>`, so the same `--run` id resumes; the daily caps use the shared ledger. `--dry` rebuilds the default lesson offline from the recorded answers to check the harness.

## What was measured (offline, estimates)
- A whole-script request is about 4,800 tokens. A per-beat request is about 3,100 to 3,400 tokens, so a five-beat lesson asks about **16,000 input tokens in five requests against 4,800 in one**: per-beat costs about 3.3 times the input tokens and five times the requests, because the fixed part of a request (system text, rules, schema, error objects, example) is about 3,000 tokens. It does not make a request fit a smaller per-minute limit by much; it makes a failed beat cheap to redo and gives a model one small job at a time. Whether the narration is better enough to pay for that is what the bake-off is for.
- At 20 requests a day a Gemini free profile can bake off only the `whole` strategy on a few lessons; Groq (1,000 a day) can afford `beat` and `beat3`.

## What is not done (said so the owner is not misled)
- No live call has been made, and none will be until the owner says the keys are in `.env`. Tested with a fake model: the prompt file, the request for a beat, per-beat writing, repair of one beat, candidates and selection, the ranking and the report, and the offline `--dry` run. Not tested: the re-asking of a beat after the whole-lesson check names it (the grouping of messages is tested, the loop is not), and any real provider.
- `narrationScore` has not been compared with human judgement; treat it as a tie-breaker among answers that already passed every rule.
- Nothing here judges whether narration is pedagogically good (first principles, a story); a person still listens. The bake-off tells which model passes the rules cheaply, not which one teaches best.
- A model must have an entry in `packages/adapters/model-profiles.json` (with limits from the provider's page) before the bake-off can use it.
